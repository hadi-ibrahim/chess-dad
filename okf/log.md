## 2026-09-24
* **Update**: identity moved **into the browser**. `profiles` and `profile_secrets` are gone: a profile is a small object in `localStorage` whose active one rides the `cd_profile` cookie, and the Lichess token lives in server memory against an httpOnly `cd_session` cookie, never in a table. The server now remembers nobody, which is what makes the app publishable without an auth system — see the rewritten [Profiles screen](concepts/profiles-screen.md) and [Persistence](concepts/persistence.md).
* **Update**: analysis is **decoupled from the profile**. `games` is now global and keyed `UNIQUE(source, external_id)`, so two players who played each other share one row and one engine run, and a new `library(scope, game_id, player_color)` table — keyed by *account*, not by profile — is the only thing that makes a game personal. A `library_games` view derives the viewer's colour, opponent, rating and accuracy, so perspective is computed rather than stored. Setting up an existing account in a second browser now links every already-analysed game instead of re-importing or re-analysing it; `linkAccountGames()` runs on any read and again on import.
* **Update**: consequences of the shared library — accuracy is stored per side (`accuracy_white`/`accuracy_black`), coaching explanations and drills are generated for **both** players' critical moments, a drill records the `color` whose move it was, and each account keeps its own SM-2 state in the new `puzzle_reviews` table. Puzzles dedupe by FEN and colour across the whole library rather than per profile. A pre-2026-09-24 database is migrated in place: games are re-filed under the account named on their own row, duplicates collapse into the copy with the most analysed positions, and schedules move to the owning account's scope.
* **Update**: the server now holds **no secret at all**. The Lichess token moved out of the process entirely: it is saved in the browser beside the profile and posted with the one import request that needs it, so a restart or redeploy no longer loses it and a compromised deployment has nothing to hand over. That required retiring the `import` [job type](concepts/job-queue.md) — a queued fetch would have had to park the token between the request and the worker — so imports now run inside their own request and only analysis stays on the queue. Deleted `src/lib/session.ts`; `/api/settings` no longer accepts a token, and reports only whether the *deployment* supplies one.
* **Update**: added the [Lessons screen](concepts/lessons-screen.md) — a beginner on-ramp at `/lessons` (nav: **Learn**) with thirteen short lessons in four groups, each with one small puzzle. It replaces the `/knowledge` screen, which rendered the raw OKF bundle to a reader who could make no use of it. Content is hand-authored in `src/lib/lessons.ts`; a puzzle is either a playable move or a multiple-choice question, judged by `move.lan === solutionUci` as on the [Puzzles screen](concepts/puzzles-screen.md), and **every position is verified against chess.js** — legal move, matching SAN, and the tactic actually holding — before it ships.
* **Update**: removed `GET /api/okf` along with the knowledge screen, since that screen was its only consumer; the bundle is read from the filesystem, not over HTTP. The handler had passed a query parameter straight into `readOkfDoc`, an unauthenticated path-traversal read, so `readOkfDoc` now confines every read to the bundle directory and allows only `.md` — the guarantee holds if a route is ever wired to it again. `POST /api/okf/progress` is unchanged, and both live consumers of the bundle still work: [coaching rules](concepts/coaching-rules.md) via `readCoachingRules()`, and progress emission via `writeProgressBundle()`.
* **Fix**: two defects on the [Lessons screen](concepts/lessons-screen.md). Each puzzle is now keyed on the lesson, because React was reusing the component instance and carrying state across — the next lesson opened already solved, with its answer drawn on the previous lesson's board and the board locked; the fault only appeared between two puzzles of the same kind, which is why it read as intermittent. The endgame lesson's queen also started on `a1`, where it was **already checking the king** down the long diagonal — an illegal position that looked like the answer had been played for you. The queen now starts on `a2`, from which `Qa8#` is the only mate in one (from `a4` both `Qa8#` and `Qe8#` mate, and a player finding the second would have been told they were wrong).
* **Update**: added `scripts/verify-lessons.mjs` and `npm run verify:lessons`, which check every lesson puzzle against chess.js — position legality (including the rule that the side *not* to move may not be in check, the gap that let the illegal endgame position ship), a live position, UCI and SAN matching what the board compares against, truthful `#` and `+` annotations, and a unique mate in one. Run it after any content change; it covers the lessons only, not the rest of the app.
* **Update**: added [Operations](concepts/operations.md) — the app is now deployable and observable. `src/instrumentation.ts` (a portable dispatcher) plus `src/instrumentation-node.ts` start the worker pool, the backup timer and a boot probe at process start, instead of the worker being started lazily by whichever request arrived first; the split exists because Next compiles the first file for the Edge runtime, where `process.on` does not exist. `GET /api/health` reports database, disk, worker and queue state and **spawns Stockfish for a real `uciok` handshake**, so a container with no engine cannot pass its rollout gate — the app otherwise boots and serves pages while failing every analysis job on a throwaway timeout. `src/lib/log.ts` emits one JSON object per line for every job lifecycle, engine spawn/exit and backup, with credential-shaped fields redacted and repetitive worker failures throttled; the engine's stderr, previously discarded outright, is now kept so an exit can be explained. `src/lib/backup.ts` and `scripts/backup-db.mjs` take `VACUUM INTO` snapshots with retention, verifying each with `PRAGMA integrity_check` *before* pruning, because an unverified backup cannot be allowed to displace a good one. Added a pinned, checksummed Stockfish installer (`scripts/setup-engine.mjs`, see [Updating Stockfish](../docs/updating-stockfish.md)), a `Dockerfile` and `railway.json`, and a unit-test suite on `node:test`.
* **Fix**: **thinking mode was silently inflating every LLM explanation ~40x and then discarding it.** DeepSeek enables thinking by default upstream and its reasoning length is unbounded: one real explanation returned **24,699 reasoning tokens over 119 seconds**, all billed as output (measured against the app's own prompt). That is far past `LLM_TIMEOUT_MS` (default 30s), so the request was aborted and replaced by the offline coach — the operator paid for the tokens and got nothing. `deepseekExplain` now sends `{"thinking": {"type": "disabled"}}` unless `DEEPSEEK_THINKING=on`. The same position went from 119,477 ms / 25,478 tokens to **1,734 ms / 632 tokens**, with no reasoning tokens and a clean result from the legality guard. Related: thinking mode also silently ignores `temperature`, so the `temperature: 0.4` the app had always sent was a no-op; it is now only sent when it will be honoured. See [Coaching rules](concepts/coaching-rules.md) and `.env.example`.
* **Fix**: the LLM **can** hallucinate chess facts, so generated explanations are now checked before they are shown. A run of 25 real explanations found that **3 of the 21 that named a move named an impossible one** (~14%), always the same shape — a confident "they can simply take it" where the capturing piece cannot reach the square ("White's knight on e2 can simply take it with Nxd5" when e2 cannot reach d5; "trades queens — after Qxb3 axb3" when e5 cannot reach b3; "take your queen with Nxc2 or Nxd3" from c4, neither of which is a knight move). The failures are **stochastic** — re-running the same positions produced *different* invented moves (`exd5`, `Qxa4`) — so prompt hardening alone cannot fix it. `illegalMovesNamed()` in `src/lib/llm.ts` now validates every move named in the text against the board (accepting moves legal in the given position or after either of the two moves it was given, so continuations pass, and skipping bare square references so "your queen on b5" is not mistaken for a move); an explanation that fails is discarded for the deterministic coach and cached as `model: "off"`. The prompt was also tightened. See [Coaching rules](concepts/coaching-rules.md).
* **Update**: the LLM is now **cost-accountable**. `src/lib/llm.ts` used to discard the provider's `usage` block, so there was no way to answer "what did that cost?"; every call now logs `promptTokens` / `completionTokens` / `totalTokens` with a running total, and `scripts/estimate-llm-cost.mjs` (`pnpm run estimate:llm`) projects the spend from the real database — eligible critical moments, minus what is already cached, times the measured ~485 tokens per explanation and ~6.6 explanations per game. Measured at `deepseek-chat` (= `deepseek-flash`): about **$0.001–0.002 per game**. The cache is what makes this structural rather than a tuning problem — a position is paid for once, so re-analysis is free.
* **Fix**: the log redaction rule matched any key containing `token`, so it swallowed `promptTokens` and friends and silently hid the LLM cost telemetry it had just been added for. Token *counts* are now allowlisted past the redaction while anything that could be a credential — `token`, `refreshToken`, `accessTokens`, `apiKey` — is still scrubbed, with a test pinning both halves.
* **Update**: restored the **games-per-account** control on the Games tab. `POST /api/import` had always accepted `max` (most recent N, per account, clamped 1..200), but the import panel stopped sending it when the Games tab was reduced to a single button — so every import silently used the `MAX_GAMES_PER_SOURCE` default of 100. The selector is back (5/10/25/50/100/200), is remembered in `localStorage` under `cd_import_max`, and the UI now says plainly, when more than one account is configured, that the number applies to each. See [Profiles screen](concepts/profiles-screen.md).
* **Fix**: three real defects the new tests surfaced, all in the analysis plumbing. `sectionUnder()` matched only level-2 headings, so `readCoachingRules()` could never read the drill text out of `tactical-motifs.md` (which uses `# How to train`) — every rule's `drill` was empty and the coach silently fell back to hard-coded text instead of the knowledge base; it is now heading-level agnostic and drops footnote definitions. `enqueueAnalyzeJobs()` did not de-duplicate repeated `gameId`s *within one call*, so `[g, g]` queued two concurrent analyses of the same game. `getJobStats().queuedGameIds` coerced SQL NULL to `0` (because `Number(null) === 0` passes `Number.isInteger`), reporting a job with no `gameId` as "game 0". Also guarded `setJobProgress` on `status='running'` so a late report cannot resurrect a finished job's lease, escaped `%`/`_` in the games search so a query like `50%` is not a wildcard, and corrected `ENGINE_POOL_SIZE`'s default to derive from `WORKER_CONCURRENCY` rather than the CPU count — raising the concurrency used to leave the extra workers blocking on a pool that had not grown with them.

* **Update**: AI coaching moved from the deployment to the **profile**. `LLM_PROVIDER`, `DEEPSEEK_*` and `OLLAMA_*` are gone from `config` and `.env.example`; a profile now owns a list of provider connections on the [Profiles screen](concepts/profiles-screen.md) — OpenAI, Anthropic, Google, DeepSeek, a local Ollama, or any OpenAI-compatible endpoint — each with a free-text model, an optional base URL, and a per-connection reasoning toggle. Keys live in `localStorage` beside the profile, are never rendered back into the DOM, and travel only in the body of the one AI request that uses them; `encodeProfile` still whitelists four public fields, so a key cannot ride the cookie. See the new [AI providers](concepts/ai-providers.md).
* **Update**: analysis now keeps the **engine baseline and AI readings side by side**. `positions.explanation` is always the deterministic engine coach, computed fresh (it is pure and offline, so `llm_cache` was retired); AI answers are rows in the new `ai_explanations`, keyed by `(fen, played_uci, classification, rating_band, provider, model)`. Several readings may exist for one position, which is what lets the review screen show "Claude last time, GPT this time" as chips — see [Review screen](concepts/review-screen.md). A position is paid for once *per model* and a cache hit is free. Migration copies the old `llm_cache` AI rows into `ai_explanations` (matched to a position by FEN) and drops the table.
* **Fix**: the highest-severity correctness bug in the [Persistence](concepts/persistence.md) review goes with it. The old explanation cache was keyed on **FEN alone**, and a FEN does not say what was played from it or who was playing — so a user could be served text written about somebody else's move, calibrated to somebody else's rating. The key now carries the played move, the classification and a 200-point rating band.
* **Update**: `POST /api/games/[id]/ai` is the only route that calls a provider. It takes the whole connection plus an optional `ply` (one move, or every flagged move, capped at 40), is request-scoped rather than queued because a queued job would have to park the key, and never stores the key. Dispatch covers four wire kinds (OpenAI-compatible, Anthropic messages, Gemini `generateContent`, Ollama chat); model ids are suggestions over a free-text field, so a newly released model works without a code change. The engine-first prompt and the illegal-move guard are unchanged, and a *connection* failure stops the run instead of repeating for every remaining position. The base URL — the only URL a user types — is validated against an https/metadata/private-address policy, with Ollama alone allowed a private address.
* **Update**: the review screen's engine button is now **Re-run engine**, distinct from the new AI actions, and asking for an AI reading no longer bounces the board back to the start of the game.
* **Update**: the suggested models were refreshed to the current lineups — Claude Opus 5.5 / Fable 5.1 / Sonnet 5 / Haiku 4.5, GPT-6 (astra, sol, luna) and the GPT-5.6/5.5/5.4 families, Gemini 3.8 Flash / 3.7 Flash / 3.1 Pro (preview) — and `temperature` is now omitted for reasoning-class models (o-series, GPT-5+, GPT-6, `gpt-chat-latest`, `deepseek-reasoner`) and for Anthropic altogether, because adaptive thinking rejects a non-default value and sending it would turn a working provider into a 400. Gemini's `generateContent` transport is unchanged: it remains fully supported. See [AI providers](concepts/ai-providers.md).
* **Update**: the model field on the [Profiles screen](concepts/profiles-screen.md) is now a **real picker** instead of a `<datalist>`, which browsers only reveal as you type and Safari barely shows at all. `POST /api/llm/models` reads the provider's own catalogue with the caller's key — `{base}/models` for the OpenAI kind, `/models` for Anthropic and Gemini (keeping only `generateContent` entries), `/api/tags` for Ollama — and the screen renders it as a filterable list, with the static suggestions shown as quick picks until it is loaded. The key is used for that one call and stored nowhere. See [AI providers](concepts/ai-providers.md).
* **Fix**: the 30-second per-call timeout was aborting a slow reasoning model ("OpenAI (GPT) did not answer within 30s"). The default is now **120s**, a connection can set its own timeout on the [Profiles screen](concepts/profiles-screen.md) (10–600s) — the person who chose a slow model is the one who knows how long to wait — and calls are **streamed** from the provider so a long generation is not mistaken for a dead connection: SSE for the OpenAI kind, Anthropic and Gemini, NDJSON for Ollama, while an arbitrary `custom` endpoint stays one-shot because it cannot be assumed to support streaming. A whole request also gained a time budget (`LLM_BATCH_BUDGET_MS`, 9 minutes): when it is spent the route stops and returns the readings it already has instead of letting the platform kill the request, and re-running resumes for free from the cache. The review screen now shows the elapsed time while it waits, and a partial run says so. See [AI providers](concepts/ai-providers.md).
* **Fix**: two defects behind "Anthropic (Claude) returned no explanation". First, **Claude 5's adaptive thinking is billed against `max_tokens`**, and the app sent 1024: on a real position the budget was spent before any answer was written, or the JSON was cut off mid-object, so the app saw empty text and reported no explanation. Anthropic now sends `max_tokens: 8192` and `output_config.effort: "low"` for the families that accept it (Haiku 4.5 rejects `effort` with a 400, so it is gated by model name). Second, the **illegal-move guard had a false positive**: real Claude output — "the Nc3/Rd1 battery", naming pieces already on those squares — was read as named moves and the explanation discarded. A non-capture token that names a piece already on its square is now read as a label, while captures are still judged, which is what every measured hallucination was. A JSON reply wrapped in a markdown fence, which Claude returns often, is now unwrapped instead of being shown verbatim. See [AI providers](concepts/ai-providers.md).
* **Fix**: Gemini suggestions and resilience. `gemini-3.1-pro` was a bad suggestion — it is not a valid `generateContent` model for the v1beta API and returned 404 — so the preview ids were dropped and the list now holds only stable ids (3.8 Flash, 3.7, 3.6, 3.5, 3.5 Flash-Lite, 3.1 Flash-Lite); **Load models** remains the authoritative list for a given key, since availability varies by account. Transient provider errors — a 503 "This model is currently experiencing high demand", a 429, a 5xx, a network blip — are now **retried up to three times** with exponential backoff and jitter, honouring `Retry-After` and sharing the call's timeout, so a whole explanation is no longer lost to a demand spike. A 404 now says to check the model id with Load models. See [AI providers](concepts/ai-providers.md).

* **Update**: the expensive routes are throttled and the synchronous analyze route is gated, ahead of a public launch. `src/lib/rate-limit.ts` adds an in-process, per-IP fixed-window limiter — 5/min for `POST /api/games/[id]/analyze`, 5/min for `POST /api/import`, 30/min for `POST /api/jobs` — keyed on the proxy's `x-forwarded-for`, and deliberately **failing open** when no address is available, since a shared "unknown" bucket would let a proxy misconfiguration lock out every user. `POST /api/games/[id]/analyze` — which runs a whole game of Stockfish inside one request — also gained the profile gate every other route has (an active profile whose account links the game), so a sweep of `/api/games/1..1000` is not even a well-formed request. A queue-depth cap and a per-account fair share remain open. See [Operations](concepts/operations.md).
* **Update**: the analysis queue now has **backpressure**. `MAX_QUEUE_DEPTH` (default 200) is how many jobs may wait at once; past it `enqueueAnalyzeJobs()` accepts only what fits and reports the rest as `rejected` with `capped: true`, and `POST /api/jobs` and `POST /api/import` say so in a `message` rather than accepting work that will not run for hours. Nothing is lost — the games are stored, and re-running the import re-queues what is still pending once the queue drains. `GET /api/health` reports `queue.depth` against `queue.capacity` so a monitor can alert before the ceiling. A per-account fair share of worker slots remains open. See [Operations](concepts/operations.md).
* **Fix**: `CHESSDAD_DISABLE_WORKER=1` was honoured only at boot, but every route that enqueues also calls `ensureWorkerStarted()` — so hitting `/api/jobs`, `/api/jobs/status` or `/api/import` turned a "web-only" replica into a consumer anyway, which is exactly the replica-steals-leases situation the flag exists to prevent. The check now lives inside `ensureWorkerStarted()` itself, so it holds for every caller. See [Operations](concepts/operations.md).
